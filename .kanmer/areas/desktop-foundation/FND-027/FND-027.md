## What

Add a root `Directory.Packages.props`, move every `PackageReference` version literal in the seven existing projects into `<PackageVersion>` items, and set `RestorePackagesWithLockFile=true` for every project (today only the three test projects set it), so the Windows App SDK and toolkit versions the desktop projects need are pinned in one reviewed place.

## Why

Proposal § 21.1 requires the target framework, Windows SDK version, Windows App SDK version, package versions, runtime identifier and signing references to be centralised, with lock files and reviewed dependency updates. Today `Directory.Build.props` centralises only compiler settings plus `$(PlaywrightVersion)`, there is no `Directory.Packages.props`, and four production projects restore without a lock file even though `packages.lock.json` is committed for all seven. Until this lands, [[DSK-02-05]] cannot pin `Microsoft.WindowsAppSDK` centrally and a major Windows App SDK bump could arrive unreviewed — the plan's decision 4 forbids that. Operator-visible consequence: an unpinned Windows App SDK major changes the package family name and breaks installed clients.
