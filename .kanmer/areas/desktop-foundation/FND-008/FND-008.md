## What

Create `docs/frd/frd-13-desktop-operator-experience.md`, register it in `docs/frd/README.md` and `docs/index.md`, add the native desktop client and the post-cutover web retirement to `docs/prd/pegasus-product.md`, and add the `DSK` capability family rows plus the updated allocation summary to `docs/capabilities.md`.

## Why

The repository's authority chain is PRD → FRD → capabilities → ADR (`docs/index.md` § Authority). Today the desktop client appears in none of them: `docs/frd/README.md` lists FRD-01…FRD-12 with FRD-12 owning the *web* operator experience, `docs/capabilities.md` holds 231 IDs across 18 families with **no desktop family**, and the PRD says nothing about a native client. That means every desktop UI ticket in areas 05 and 06 has required behaviour with no functional-requirements owner, and `docs/capabilities.md` — the join between an ID and its canonical owner — cannot answer "which document owns this outcome". Proposal §26 requires the product/UI documentation set; the Phase 0 target state in the area plan § 4 says FRD-13 and the PRD update are merged and `docs/capabilities.md` carries the `DSK` family. [[DSK-00-05]] must land first so FRD-13 can cite accepted ADRs rather than plans.

Draw the FRD-12 / FRD-13 boundary first and write it into the ticket plan: FRD-12 keeps the web operator experience until cutover; FRD-13 owns the **desktop** operator experience (shell and navigation, session and first run, keyboard completion, accessibility baseline, error and empty states, update-required behaviour). Overlapping normative text in two FRDs is a defect.
3. Create `docs/frd/frd-13-desktop-operator-experience.md` using the template in `docs/frd/README.md` verbatim: the `> Owner capabilities: … · Source PRD: … · Design: docs/design/README.md#…` line, then `## Purpose`, `## Behaviour`, and the remaining headings the template lists.
4. Write `## Behaviour` as normative rules with "must"/"never"/"fails closed" — for example: an unsupported client version must not proceed (ADR-0105); every critical workflow must be completable from the keyboard; a field is a label and a control, and operator-facing explanation is a defect (`docs/design/README.md`, `AGENTS.md` § Simplicity rails); no colour-only state. Cite `docs/desktop/06-ui-design/screen-specs.md` for per-screen detail instead of copying it.
5. Cite the accepted ADRs rather than the plan set: ADR-0100 (native client), ADR-0102 (session), ADR-0104 (online-required), ADR-0105 (minimum version), ADR-0108 (report rendering, still `proposed` — mark it as such).
6. Add the FRD-13 row to the documents table in `docs/frd/README.md`, with its capability families (`DSK`, and `UI` where it extends FRD-12's domain).
7. Add the `DSK` family rows to `docs/capabilities.md` under `## Capabilities` using the existing column order `| ID | Durable outcome | Horizon | Target release | Canonical owner | Activation/boundary |`, one row per durable desktop outcome, with `Canonical owner` linking to FRD-13 or the owning ADR.
