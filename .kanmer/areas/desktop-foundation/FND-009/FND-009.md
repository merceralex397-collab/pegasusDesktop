## What

Add the two release-tag conventions to `docs/engineering.md` § Branches and delivery — `gateway/r<N>` where N is the release number in `docs/operations.md` § Production environment, and `desktop/v<M.m.b>` equal to the MSIX package version — mirror them into `.agents/skills/pegasus-release/SKILL.md`, and have the release actor apply the first `gateway/r<N>` tag at the next production release.

## Why

The fork has **no tags at all** (`git tag`, 2026-08-23) and the release record in `docs/operations.md` identifies releases by number and source SHA in prose. Once the desktop ships, the App Installer manifest carries a compatibility range expressed in versions, and the gateway's minimum-client-version gate (ADR-0105) has to be traceable to the commit that shipped it: without tags, "which gateway release does desktop v1.2.3 require" is answered by reading paragraphs. The area plan's branching flow item 4 fixes both conventions and ties them to CI: unsigned MSIX on every PR, signed on `main` tags only. [[DSK-09-17]] later builds a `desktop/v*` tag-triggered sign-and-publish lane on top of this convention, so the naming has to be settled before that lane is written.
