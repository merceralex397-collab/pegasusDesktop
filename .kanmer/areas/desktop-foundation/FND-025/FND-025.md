## What

Produce a per-folder characterization-test gap list for `src/Pegasus.Core` (Intake, Workflow, Lifecycle, Assessment, Vehicle, Triage, Reports, Tasks, Custody, Documents, Operations, Identity, ReferenceData, Eva, ImageIntake, Address, Cases) naming the lowest reliable test boundary for each gap, and write the target dependency rules that area 02 will turn into architecture tests.

## Why

Proposal §22.1 requires, before any current business rule is moved, that the entry point is identified, fixtures created, existing results captured, the behaviour judged intentional or accidental, and a characterization test written at the lowest reliable boundary — "This prevents a clean rewrite from silently losing obscure business behaviour." §24 Phase 0's fourth exit-gate item is "Target dependency rules compile as architecture tests or documented checks." Operator-visible consequence: an untested Core policy that changes meaning during the conversion produces a wrong case status, a wrong fee note or a wrong allocation, with no failing test to catch it. The `gap:` cells written by [[DSK-01-03]] and [[DSK-01-04]] are direct inputs; area 02 consumes the dependency rules and area 08 consumes the gap list.

Use the `test-gap-analysis` skill to structure the pass; do not eyeball it.
5. For each uncovered or partially covered policy, name the **lowest reliable boundary** at which a characterization test can be written, using the tier vocabulary of `docs/engineering.md` § Required evidence tiers: tier 2 Core/domain for a pure policy, tier 3 parser/adapter contract for an extraction or format rule, tier 4 LocalDB persistence for a concurrency, lease or reference-allocation rule, tier 5 Web/API/MCP caller only where the behaviour is observable solely through the route. Lower is better; a rule provable at tier 2 must not be pushed to tier 5.
6. For each gap, record the four things §22.1 demands before a rule may move: the current entry point (`path:line`), the fixture source (a real path under `reference/`, or a named `corpus/` cohort — never invented data), the existing result and side effects to capture, and whether the behaviour looks intentional or accidental. Where it looks accidental, say so and mark it "needs approval before change" — do not propose a fix.
7. Apply the `assertion-quality` skill to the existing tests of the two highest-risk policies (`src/Pegasus.Core/Lifecycle/CaseLifecycle.cs` and `src/Pegasus.Core/Triage/TriageLifecycle.cs`): a test that asserts only "no exception" is a gap even though a test file exists. Record those as gaps with the reason.
8. Fold in every `gap:` cell from [[DSK-01-03]] and [[DSK-01-04]] so the parity matrix and the gap list agree, and cross-reference each list entry to its `PAR` row id.
9. Write the target dependency rules for area 02 as a numbered, testable list — each one phrased so it can become an assertion in `tests/Pegasus.ArchitectureTests/DependencyDirectionTests.cs`. At minimum: the desktop projects must not reference `Pegasus.Infrastructure`; must not reference EF Core (`Microsoft.EntityFrameworkCore*`); must not reference any Azure SDK (`Azure.*`, `Microsoft.Azure.*`); must not reference `Box.Sdk.Gen`, Playwright or Graph packages; must not reference `Pegasus.Web`; and `Pegasus.Core` must keep zero package references. State each as "assembly X must not (transitively) reference Y" so the existing reflection helper `tests/Pegasus.ArchitectureTests/TypeInspection.cs` can evaluate it.
10. Confirm the rule set against the current tests: read `tests/Pegasus.ArchitectureTests/DependencyDirectionTests.cs` and state, per rule, whether it is already asserted, needs extending, or is new. Do not write the tests here — area 02 owns that work; this ticket delivers the targets.
