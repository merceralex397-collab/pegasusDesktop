## What

Measure and record the **web application's** baseline on the named lowest-spec office workstation against the local production-mimicking stack — cold and warm page timings, list paging, report generation, and memory — and list the critical business fixtures by path, so proposal §15.1's desktop budgets have something real to be judged against.

## Why

Proposal §15.1 gives provisional desktop budgets (cold launch ≤ 3 s p95, warm ≤ 1.5 s, cached navigation ≤ 200 ms, first page of ordinary results ≤ 1 s, ordinary save ≤ 1 s, idle CPU below 1 %, steady memory below 500 MB) and says explicitly "Baseline hardware and data sizes must be recorded. Adjustments require evidence, not convenience." §24 Phase 0 lists "Record baseline performance and critical business fixtures" as Phase 0 work. Operator-visible consequence: without a recorded baseline, "the native app feels faster" is an opinion, and a release candidate can regress without anyone being able to prove it. Area 10's `DSK-10-10` publishes the final budget table from this capture; area 08's `DSK-08-15` re-runs the same workflows against the desktop.

## Implementation steps

1. Orientation. Read `docs/desktop/01-inventory-and-parity/README.md` §§ 2–4 and § 7, `docs/desktop/10-security-observability-performance/README.md` §§ 2–4, proposal § 15.1 and § 15.3, and `docs/runbook.md` § Local setup and run. Call `get_doc_gates` for this ticket id, then `take_ticket`.
2. **Operator step** — name the baseline machine. The operator identifies the lowest-spec supported office workstation and hands back: CPU model, physical cores, installed RAM, storage type, GPU, Windows 11 edition and build, display resolution and scaling, and whether the machine is on the office LAN or VPN. Nothing may be treated as a pass/fail budget until this line exists (`docs/desktop/10-security-observability-performance/README.md` § 2 Assumptions).
3. Confirm prerequisites on that machine: `pwsh ./scripts/Invoke-Doctor.ps1` — expected: every prerequisite reported present. Record the .NET SDK version, the LocalDB or SQL container in use, and the Azurite version.
4. Bring up the local production-mimicking stack: `pwsh ./scripts/Invoke-LocalDevelopment.ps1 -Action Start`, then `-Action Status` and `-Action Smoke`. Expected: the manifest state is `Running` and the smoke check passes. If `DSK-08-17`'s `TestStack` mode has landed, use it instead and say which mode produced the numbers.
5. Record the data sizes the measurement runs against, in tier-10 vocabulary (`docs/engineering.md:72-89`): number of cases, cases per stage, documents per case, retained mail rows, asset-metadata rows. Numbers come from the seeded local database — state how it was seeded. **Never fabricate VRMs, names, addresses or emails**; fixtures come from `reference/` or the ignored, immutable `corpus/` (`AGENTS.md` § Safety rails).
6. Build the measurement script for the web app in release configuration only (proposal §15.3: release builds and representative production-like data). For each workflow capture at least 20 samples and report p50 and p95, not a single reading: cold first request after start, warm repeat request, dashboard, case list page 1 and a deep page, case detail, inbox list, inbox message, and an ordinary save on the case workspace.
7. Time report generation separately — `OnPostGenerateReportDraftAsync` on `src/Pegasus.Web/Pages/Cases/Assessment/Index.cshtml.cs` — and record the first render (Chromium startup cost) apart from subsequent renders, because `src/Pegasus.Infrastructure/Reports/PlaywrightAssessmentReportRenderer.cs` serialises renders behind a `SemaphoreSlim(1,1)` and caches the browser.
8. Capture process metrics with the `dotnet-trace-collect` and `analyzing-dotnet-performance` skills: idle CPU, working set after start, working set after repeated navigation, and any sustained growth. Save the trace artefacts under an ignored local path and reference them by name; do not commit binaries.
9. Record the operator-facing latency of the two heaviest list surfaces (case list and inbox) at the page sizes the web app actually uses, so area 06 can size the virtualized desktop lists against a real number rather than a guess.
10. List the critical business fixtures by path — the specific files under `reference/` used for the assessment/report and intake workflows, plus a named (not copied) reference to the `corpus/` cohort where one was used. One line per fixture: path, what it exercises, and which workflow it feeds.
11. Write the results into `docs/desktop/10-security-observability-performance/README.md` as a dated "Baseline capture — web app" subsection under § 2 Evidence base: the workstation line, the data sizes, the p50/p95 table per workflow, the memory and CPU figures, and the exact commands that produced each number. State plainly that `DSK-10-10` owns publishing the §15.1 budget table and that these numbers are the comparison baseline, not the budgets themselves.
12. Write the same content plus the raw sample data into the ticket `research` document with `set_ticket_doc`, tick every `open-questions/` item, run the Verification checks, then `get_doc_gates` and move to Done.

## Guardrails

- **Azure**: no write, and no Azure measurement. L-02 and ADR-0014 mean there is no Azure test environment; asking for one, or load-testing production, is out of bounds. Production timings, if ever needed, come from the pilot ring under separate approval.
- **Scope boundary**: this ticket runs the local stack and measures. Editable files: `docs/desktop/10-security-observability-performance/README.md` and `docs/open-decisions.md`. It must not change application code to make a number better, add a benchmark project, or commit trace, dump or corpus artefacts.
- **Traps**: performance budgets judged on a fast developer machine are worthless — measure on the recorded baseline workstation in release builds only; `corpus/` is ignored and immutable and domain data must never be fabricated; App Insights is capped at 0.1 GB/day, so telemetry is not a substitute for local measurement; a local full-privilege run proves nothing about deployed permissions (upstream `PLAT-035`), so do not present these numbers as production evidence.
- **Markdown placement**: no new `.md` outside `docs/(prd|frd|adr|design|desktop)`; measurement artefacts stay local and are referenced by name.
- **Simplification pass** (`AGENTS.md` step 4): required over this branch diff before the PR — `n/a — docs-only` if the only diff is the baseline subsection.
