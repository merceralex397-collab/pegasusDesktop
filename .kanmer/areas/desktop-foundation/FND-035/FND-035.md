## What

Make Pegasus single-instance per Windows user: register a key with `AppInstance.FindOrRegisterForKey`, and when this process is not the owner, redirect the activation to the running instance with `RedirectActivationToAsync` and exit — all of it before any window is created — while the running instance handles the redirected activation and navigates to the requested case or document.

## Why

Proposal § 7.3 requires that a second launch activates the existing window, that deep links and file activations are redirected to the active process, and that unsaved work is never duplicated across processes. Plan § 3 decision 8 fixes the mechanism and the ordering constraint (redirect before window creation) and rules multi-window out of Phase 1. The Phase 1 exit gate ([[DSK-02-16]]) has a dedicated "Single instance" row: a second launch must activate the first window. Operator-visible consequence: two Pegasus windows editing the same case is exactly the silent-overwrite failure the concurrency design exists to prevent.

## Implementation steps

1. Orient: read the plan row and the plan sections named under Source of truth, then `get_doc_gates <this ticket id>` and `take_ticket` on branch `task/desktop-single-instance` from `origin/dev`.
2. Establish the mechanism from official documentation before writing code: `microsoft_docs_search` for `AppInstance.FindOrRegisterForKey` redirection semantics and for the Windows App SDK app-lifecycle single-instancing sample. Confirm two facts and record them with URLs in the ticket research document — (a) whether the redirect must run before `Application.Start`, and (b) whether that requires defining `DISABLE_XAML_GENERATED_MAIN` and writing an explicit `Program.Main`.
3. If an explicit entry point is required, add `<DefineConstants>$(DefineConstants);DISABLE_XAML_GENERATED_MAIN</DefineConstants>` to `src/Pegasus.Desktop/Pegasus.Desktop.csproj` and create `src/Pegasus.Desktop/Program.cs` with a `[STAThread] static void Main(string[] args)`. If the documentation shows the redirect is safe from `App.OnLaunched`, implement it there instead and record why.
4. In the entry point, call `AppInstance.GetCurrent().GetActivatedEventArgs()`, then `AppInstance.FindOrRegisterForKey(<key>)`. The key must be constant per Windows user — use a fixed application key string (the package family name is already per-user scoped by the instancing API); do not build a key from a mutable value such as the window title or a version number.
5. When `FindOrRegisterForKey` returns an instance that is not current, call `RedirectActivationToAsync(args)` and terminate the process immediately without creating a window, a host or a log file beyond one redirect line. Nothing else may run in the redirected process.
6. In the owning instance, subscribe to `AppInstance.Activated` and forward the redirected `AppActivationArguments` to a `IActivationRouter` service registered in `Hosting/PegasusHost.cs`. The router parses deep-link and file arguments and asks `INavigationService` ([[DSK-02-08]]) to navigate to the requested case or document; an argument it does not understand is logged and ignored, never crashed on.
7. Bring the existing window forward on redirect: restore it if minimised and activate it. Use `winui-design` / `microsoft_docs_search` for `AppWindow` activation to confirm the supported call rather than guessing at a Win32 interop.
8. Log every activation and redirect with the per-launch session identifier from [[DSK-02-07]] into the single-instance/activation log — [[DSK-02-11]] includes that log in the diagnostics bundle, so the line format must be stable and redacted.
9. Add view-model/unit tests in `tests/Pegasus.Desktop.ViewModelTests` for the argument parsing and routing: a case deep link routes to the case route with the right identifier, a file activation routes to the document route, an unknown argument is ignored and logged. Instancing itself cannot be unit-tested; that is the UI test below.
10. Prove the behaviour end to end: install or run the packaged app, then launch it twice. Use `winapp run` (never the packaged `.exe` directly) and confirm exactly one window exists and that the second launch's arguments reached the first window. If the [[DSK-08-06]] `winapp ui` harness exists, add a `single-instance` batch to it; otherwise record a manual pass with a screenshot and name [[DSK-08-06]] as the automation follow-up.
11. Confirm no multi-window capability was added — Phase 1 is single-window only (plan § 3 decision 8). Then run the simplification pass, record it under a dated `## Simplification pass` heading in the ticket plan, and open the PR into `dev`.

## Acceptance criteria

- [ ] A second launch under the same Windows user activates the first window; exactly one process remains.
- [ ] The redirect happens before any window, host or view model is created in the redirected process.
- [ ] Deep-link and file activation arguments reach the running instance and navigate it; unknown arguments are logged and ignored.
- [ ] The instance key is constant per user and derives from no mutable value.
- [ ] Every activation and redirect is logged with the session identifier in the stable activation-log format.
- [ ] No multi-window capability is introduced.
- [ ] The mechanism decision (explicit `Main` vs `OnLaunched`) is recorded with its documentation URL in the ticket research.
