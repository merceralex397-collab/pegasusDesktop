## What

Build the native WinUI 3 sign-in screen that replaces `Pages/Account/SignIn.cshtml.cs`, and render every row of the session-failure matrix — invalid credentials, rate limited, account disabled, password change required, client unsupported, server unreachable — as an inline state on that screen or a routed screen, never as a modal dialog.

## Why

Proposal § 8.1 requires the login screen to stay a Pegasus login: username and password, the same account store, no Microsoft-account prompt and no dependency on the workstation's Windows identity. Proposal § 8.4 requires the desktop to *distinguish* the failure kinds rather than report everything as bad credentials — a user whose account has been disabled, or whose client is below the minimum version, must be told what actually happened. Without this ticket [[DSK-04-07]] has no operator surface and the Phase 2 exit gate "current user credentials work" cannot be evidenced.

## Implementation steps

1. Orientation. Read `docs/desktop/04-auth-session-update-and-startup/README.md` § 3 *Session failure matrix* and `docs/desktop/06-ui-design/screen-specs.md` § 13.1 in full — the AutomationIds and copy rules there are binding, not suggestions. Call `get_doc_gates <this ticket id>`, then `take_ticket`.
2. Load `pegasus-desktop`, then `winui-design`. Before writing any XAML, follow that skill's *Search samples before writing XAML* section and run `winui-search.exe` for the sign-in form controls; then read its *XAML landmines* and *Theming rules* sections. Use only theme resources from [[DSK-02-09]] — no colour literals.
3. Add `SignInPage.xaml` / `SignInPage.xaml.cs` and `SignInViewModel` to `src/Pegasus.Desktop` under a `Session/` capability folder. The frame is navless with the logo and the company name (`_LayoutAuth` convention), fields **User name** and **Password** with label plus control only, and a primary **Sign in** button. Set `AutomationProperties.AutomationId` to exactly `SignIn.UserName`, `SignIn.Password`, `SignIn.Submit` and `SignIn.Problem`.
4. Implement the five sign-in states from the screen spec as view-model state, not as dialogs: idle; signing in (button disabled, thin indeterminate progress); invalid credentials; rate limited; and the routed states below. Show messages in an `InfoBar` bound to `SignIn.Problem` — the plan row is explicit that routine states get an `InfoBar`, never a modal.
5. Reuse the gateway's operator copy verbatim so desktop and web say the same thing: the invalid-credential sentence from `src/Pegasus.Web/Pages/Account/SignIn.cshtml.cs:72-74`, and "Enter your username." / "Enter your password." for the empty fields. Return focus to the User name field after an invalid attempt and clear the password box.
6. Map the remaining matrix rows: `RateLimited` → "Try again in a minute" with the submit button disabled until the `Retry-After` seconds elapse; `AccountDisabled` → the disabled-access sentence with no retry loop; `PasswordChangeRequired` → navigate to the Change password screen (`Password.Current`, `Password.New`, `Password.Confirm`, `Password.Save`); `ClientUnsupported` → navigate to the Update required screen (`Update.Required.Now`, `Update.Required.SignOut`); `Unreachable` → a connectivity sentence, never an invalid-credentials message.
7. Add the Update required / Blocked screen as a full-window, rail-less page per the screen spec: title "Update required", the current and minimum versions shown as values, one primary action "Update now" and a secondary "Sign out"; the Blocked variant shows the operator sentence and "Sign out" only, with `Blocked.Reason` on the message. Wire "Update now" to the update entry point [[DSK-04-09]] exposes; if that ticket has not landed, bind it to a command that logs and disables itself, and say so in the plan document.
8. Apply the keyboard and focus rules from `docs/desktop/06-ui-design/keyboard-and-accessibility.md`: `Tab` order User name → Password → Sign in; `Enter` submits from either field; every interactive control has an `AutomationId`; the error message is announced (associate it with the fields, do not rely on colour alone).
9. Write view-model tests in `tests/Pegasus.Desktop.ViewModelTests` — one test per matrix row — asserting the resulting state, the message identity and whether submit is enabled. These run without a `DispatcherQueue`.
10. Build and launch with `.\BuildAndRun.ps1` from `.codex/skills/winui-dev-workflow/` (invoke it asynchronously; it prints the app PID). Load `winui-ui-testing`, then add the seven session-failure cases to `tests/Pegasus.Desktop.UITests/ui-tests.ps1` — **do not author a second harness**. That file's contract is owned and pinned by [[DSK-08-06]]: the signature is `param([Parameter(Mandatory)][int]$AppPid)` (never `$Pid`, which is read-only in PowerShell) and the pass/fail counter is its `Test-UI` helper. Add each matrix row as a `Test-UI` case driven against a stubbed gateway, asserting with `winapp ui wait-for` / `get-value` — never `Start-Sleep`. If [[DSK-08-06]] has not landed yet, create the file from the `winui-ui-testing` script template with exactly that signature and that helper so the two cannot fork, and record in the plan document that [[DSK-08-06]] takes ownership of the skeleton when it lands.
11. Capture a `winapp ui screenshot` for each of the seven states (idle, signing in, invalid credentials, rate limited, account disabled, update required, disconnected) and attach them to the ticket proof.
12. Run the accessibility audit section of `winui-ui-testing` over the sign-in and update-required windows and record the result; a control without an `AutomationId` is a defect, not a warning.
13. Run the simplification pass over this branch's diff, record it under a dated `## Simplification pass` heading in the plan document, then open the PR into `dev`.
