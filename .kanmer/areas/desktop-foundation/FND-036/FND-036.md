## What

Add the desktop's crash path — handlers for `Application.UnhandledException`, `AppDomain.CurrentDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException` that write a diagnostics bundle and then exit — and the user/administrator "Export diagnostics" command that produces the same bundle on demand as a zip with a documented manifest.

## Why

Proposal § 16.3 requires that crash handling never swallows exceptions and continues in a corrupted state and that a diagnostics bundle can be exported by the user or administrator; § 18.1 fixes its contents — structured rolling local logs, a per-launch session identifier, API correlation identifiers, redaction by default, bounded size and retention, and app version, Windows version, package identity and dependency versions. Plan § 3 decision 10 makes the bundle a foundation feature rather than a Phase 8 afterthought, because with ten users and no central desktop telemetry (ADR-0109) the bundle *is* the support channel. Operator-visible consequence: when a workstation misbehaves, the operator's only evidence is the file this ticket produces.

## Implementation steps

1. Orient: read the plan row and the plan sections named under Source of truth, read `docs/desktop/06-ui-design/screen-specs.md` § Diagnostics and settings, then `get_doc_gates <this ticket id>` and `take_ticket` on branch `task/desktop-diagnostics-bundle` from `origin/dev`.
2. Define the bundle manifest as a versioned JSON schema in `src/Pegasus.Desktop.Infrastructure/Diagnostics/DiagnosticsBundleManifest.cs` with `schemaVersion` and exactly the fields the plan and proposal § 18.1 name: app version, package identity (`Package.Current.Id.FamilyName`, `Name`, `Publisher`, `Version`), Windows version, Windows App SDK and dependency versions, channel, per-launch session identifier, bundle creation timestamp, and the reason (`crash` | `user-export`). Write the schema into the ticket plan too, so the schema test and the support runbook agree.
3. Implement `DiagnosticsBundleBuilder` in `src/Pegasus.Desktop.Infrastructure/Diagnostics/`: it collects the manifest, the redacted rolling log files from the [[DSK-02-06]] writer, the last compatibility response held in the bounded cache, and the single-instance/activation log from [[DSK-02-10]], then writes a zip. Nothing outside that list may enter the bundle — no attachment content, no case data, no credentials (proposal § 18.1).
4. Apply redaction at collection, not only at write: re-run the [[DSK-02-06]] redaction over every file copied into the bundle so a log written before a redaction-rule fix cannot leak.
5. Register the three unhandled-exception handlers in `src/Pegasus.Desktop/App.xaml.cs`: `Application.Current.UnhandledException`, `AppDomain.CurrentDomain.UnhandledException` and `TaskScheduler.UnobservedTaskException`. Each writes a `crash` bundle, flushes the log sink, and then exits the process. Do not set `e.Handled = true` and continue — continuing in a corrupted state is explicitly forbidden by proposal § 16.3.
6. Bound the crash path: the handler must complete within a short, explicit timeout and must never itself throw; wrap the bundle write in a try/catch whose fallback is a single plain-text line to the log directory. A crash handler that hangs looks identical to a hung application.
7. Add the "Export diagnostics" command to the Diagnostics section of the settings route, with `AutomationProperties.AutomationId="Settings.ExportDiagnostics"`, plus "Open logs folder" (`Settings.OpenLogs`). The export writes the same bundle with reason `user-export` and shows the operator the produced path — one sentence, no explanatory copy (`docs/design/README.md`).
8. Bound retention: bundles are written under the packaged app's local folder with a maximum count and total size, oldest deleted first, so the bundle mechanism cannot itself fill a workstation disk (ADR-0104, proposal § 18.1 "bounded size and retention").
9. Add a bundle schema test in `tests/Pegasus.Desktop.ViewModelTests`: build a bundle from a fixture directory, open the zip, and assert the manifest parses, carries every required field, and that the archive contains the log and activation-log entries and nothing else.
10. Add a fault-injection test: register the handlers against a fake application surface, raise an unhandled exception, and assert that a `crash` bundle was written and that the process-exit action was invoked exactly once. Also assert a planted bearer token in a fixture log is absent from the bundle.
11. Prove it on a real launch: run the packaged app, trigger the export command, and confirm the zip contents against the manifest; then trigger a deliberate unhandled exception in a temporary debug-only command, confirm a crash bundle appears and the app exits, and remove the temporary command before the PR.
12. Run the simplification pass, record it under a dated `## Simplification pass` heading in the ticket plan, and open the PR into `dev`.

## Acceptance criteria

- [ ] All three unhandled-exception sources are handled; each writes a bundle and exits; none marks the exception handled and continues.
- [ ] The bundle is a zip containing a versioned manifest with app/package/Windows/dependency versions, channel, session identifier, timestamp and reason.
- [ ] The bundle contains the redacted rolling logs, the last compatibility response and the activation log — and nothing else.
- [ ] Redaction is re-applied at collection; no token, refresh token, password or attachment content can appear.
- [ ] "Export diagnostics" exists on the Diagnostics settings route with AutomationId `Settings.ExportDiagnostics` and reports the produced path in one sentence.
- [ ] Bundle retention is bounded by count and total size, oldest first.
- [ ] The crash path is time-bounded and cannot throw.
