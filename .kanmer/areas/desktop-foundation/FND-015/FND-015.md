## What

Bring the parity-matrix rows for proposal §13.1 (access and session) and §13.2 (dashboard and work queues) — `PAR-01`, `PAR-02`, `PAR-03`, `PAR-04`, `PAR-05`, `PAR-06`, `PAR-42`, `PAR-44` — to status `inventoried` (or `legacy path retained` for `PAR-42`), with entry point, handlers, behaviour evidence, FRD owner, capability group and at least one test file recorded per row.

## Why

Proposal §23 makes the matrix the parity contract and §23.1 lists the evidence each row must eventually carry; §24 Phase 0's exit gate is "every current production capability has an inventory row". Access and session is the first thing the desktop replaces (proposal §8), so a wrong or thin row here mis-specifies the login screen, the forced-password-change state and the role-aware shell. Operator-visible consequence: an operator who could sign in to the web app but cannot sign in to the desktop, because a lockout, rate-limit or `MustChangePassword` behaviour was never inventoried. The skeleton comes from [[DSK-01-01]]; the flow detail behind these rows is completed by [[DSK-01-06]]; area 04 builds the login and session work from these rows.
