## What

Execute the dispositions in `docs/desktop/01-inventory-and-parity/upstream-kanmer-carryover.md` **as corrected by the 2026-08-24 coverage pass recorded on group `EPIC-014`**: **verify** the 19 upstream tickets that no seeded conversion ticket covers and that that pass has already imported under `EPIC-014`, confirm the 21 board tickets that carry an added acceptance line instead of a new ticket, list the 75 dropped rows without recreating any of them, and re-run the classification against the upstream head that is current when this ticket runs — importing only what a later head adds. Every imported ticket carries its upstream id in the ticket **title** (`upstream:<ID> · <title>`) and in its **labels** — never in `refs`, which accepts only repository-relative paths to documents that exist — with the original body and the upstream labels. This is **not** a flat recreation of the triage table, and it is no longer the batch's first creation.

## Why

The original repository is not a finished project: its board carried 109 open, non-archived tickets when the triage was written on 2026-08-23, and **114** at head `a5b28111` on 2026-08-24. L-05 makes the fork's board the single work register for the conversion, so anything real that is not carried over is silently lost. Operator-visible consequence: production defects already reported upstream — a triage-request email that creates neither a Triage nor an Unidentified item (upstream `INTK-033`, board [[INTK-007]]), a live receipt-processing defect nobody on the board is permitted to fix (upstream `INTK-027`, board [[INTK-004]]), an EVA package EVA refuses to import (upstream `ENG-014` and upstream `ENG-015`, board [[ENG-001]] and [[ENG-002]]) — would disappear from the fork's backlog and be rediscovered by an operator instead of a ticket. The opposite failure is just as real and is the reason this ticket was rewritten: executed as a flat 57-ticket recreation it would have created roughly twenty duplicate or near-duplicate tickets, fifteen of them for work named seeded tickets already deliver, two for commits already merged into the fork's `main`, one moot with the Razor front end, and two for decisions `FEAT-043` already owns. A duplicate backlog row is not harmless — it competes for the same code with a different acceptance criterion. The 19 imports were then created on **2026-08-24** by the coverage pass itself, so what is left here is an audit of that batch plus the delta a later upstream head opens; running the creation recipe again over tickets that already exist would produce the very duplication this ticket was rewritten to prevent, because `create_items` is ungated and duplicates rather than fails.
