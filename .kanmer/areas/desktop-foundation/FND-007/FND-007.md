## What

Write ADR-0108 — report rendering moves to the desktop through an isolated, never-visible WebView2 HTML→PDF path, with the gateway renderer retained until golden-file parity passes — and merge it with `status: proposed`. Flip it to `accepted` only after Phase 7 validates the documented `HWND_MESSAGE` controller from the packaged desktop app and the golden-file tests pass. The authoring and first merge belong to **Phase 0**: plan 00 § 4 Target state makes ADR-0100…ADR-0110 part of the Phase 0 governance exit gate and allows ADR-0108 to stand `proposed` until Phase 7 packaged-controller validation and parity, so this ticket is grouped `HZN-001` and only the step-10 acceptance flip waits on [[DSK-07-14]]/[[DSK-07-15]].

## Why

Locked decision L-03 puts report rendering on the desktop, but it is the one place the conversion deliberately uses WebView2 at all — proposal §2.1 forbids a WebView shell, and §23.2 allows an isolated WebView2 use only when "it requires an ADR and must not host Pegasus UI". Without that ADR on record, the first desktop renderer commit reads as a violation of the locked constraint. The decision cannot honestly be `accepted` yet either: Microsoft Learn documents `HWND_MESSAGE` as the invisible parent for `CoreWebView2Controller`, but Pegasus still needs Phase 7 evidence that the fixed controller initialises and prints from the packaged desktop app and meets golden-file parity. Meanwhile ADR-0025 and ADR-0028 keep the integrated renderer running in the Web Container App, so the retained-until-parity clause has to be explicit or the two decisions look contradictory.
