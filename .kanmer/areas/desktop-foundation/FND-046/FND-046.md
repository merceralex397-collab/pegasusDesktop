## What

Make the desktop shell role-aware: derive the signed-in actor's rights from the session claims through `StaffAuthorization`, hide the Administration rail item and admin-only commands for non-administrators, and prove with an integration test that the gateway still refuses a forged call from a client that shows the command anyway.

## Why

Proposal § 8.3 is explicit that hiding commands is a usability affordance only: "the gateway must independently enforce authorization for every data query and command". `docs/desktop/06-ui-design/screen-specs.md` further requires Administration to be **absent**, not disabled, for non-administrators. The operator-visible consequence of getting this wrong in either direction is a rail full of commands a user cannot run, or — far worse — a client-side check treated as the security boundary.

## Implementation steps

1. Orientation. Read `docs/desktop/04-auth-session-update-and-startup/README.md` § 5 row `DSK-04-10` and `docs/desktop/06-ui-design/screen-specs.md` § *Shell*. Call `get_doc_gates <this ticket id>`, then `take_ticket`. Load `pegasus-desktop`, then `winui-design`.
2. Read `src/Pegasus.Core/Identity/StaffAuthorization.cs` and `src/Pegasus.Core/Identity/IdentityContracts.cs` end to end. `Pegasus.Core` is referenced directly by `Pegasus.Desktop` (`docs/desktop/02-architecture-and-foundation/README.md` § 4), so the desktop must **reuse** `StaffAuthorization.IsAuthorized` — do not copy the matrix or re-express it in the view model. A second implementation of a business rule is a defect under `docs/engineering.md` § One Core owner.
3. In `src/Pegasus.Desktop.Infrastructure` `Session/`, build the actor from the session claims exactly as the gateway does: take the subject id and the role-name claims from the access token and call `StaffActorFactory.TryCreate(subjectId, roleNames, out var actor)`. A `false` return is a failed session, not an anonymous one — surface it as a session failure and return to sign-in.
4. Expose the actor from a `ICurrentActor` service registered in the host, refreshed whenever the session changes (sign-in, refresh, sign-out). Never cache rights across a sign-out.
5. In the shell view model from [[DSK-02-08]], compute rail-item visibility from `StaffAuthorization.IsAuthorized(actor, right)`. Bind the Administration item's presence to `ManageStaffAccounts` (the Administrator-only family in `StaffAuthorization.cs:44-51`) and **remove** the item from the `NavigationView.MenuItems` collection when unauthorized — do not set `IsEnabled=false`, the screen spec requires absence.
6. Apply the same rule to admin-only commands anywhere on the shell (title-bar user menu entries, command-bar buttons). Keep the rail order from the screen spec unchanged when items are removed: Dashboard → Inbox → Upload → Queues → Cases → Operations → Administration → user.
7. Preserve the AutomationIds: `Shell.Rail.<Route>` for each present rail item and `Shell.Title.User`. A hidden item has no AutomationId in the tree, which is what the UI test asserts.
8. Add a navigation guard: if a route is reached by any means other than the rail (deep link, restored state), re-check `StaffAuthorization.IsAuthorized` before navigating and route to the dashboard with a message when it fails. This is still a usability guard, not the security boundary.
9. Write view-model tests in `tests/Pegasus.Desktop.ViewModelTests`: an `Administrator` actor sees Administration; an `Engineer` and a `User` actor do not; a `TryCreate` failure produces a session failure; the rail order is unchanged after removal.
10. Write the server-side half of the proof as an integration test in `tests/Pegasus.IntegrationTests`: authenticate as a non-administrator, call an Administrator-only `/api/v1` endpoint directly with a valid bearer token, and assert the response is a `urn:pegasus:problem:not-authorized` problem — proving the gateway refuses the call whether or not the client hid the command. Place the test in exactly one shard and keep `pwsh ./scripts/Invoke-TestShard.ps1 -VerifyPartition` green.
11. Build and launch with `.\BuildAndRun.ps1` from `.codex/skills/winui-dev-workflow/`, sign in once as an Administrator and once as a non-administrator, and capture `winapp ui inspect -a <pid> --interactive` output plus a screenshot for each — the non-administrator tree must contain no `Shell.Rail.Administration`.
12. Run the simplification pass over this branch's diff, record it under a dated `## Simplification pass` heading in the plan document, then open the PR into `dev`.

## Acceptance criteria

- [ ] Administration is absent from the rail for `Engineer` and `User` actors and present for `Administrator`.
- [ ] Visibility is computed by calling `StaffAuthorization.IsAuthorized`; no role matrix is duplicated in the desktop projects.
- [ ] The rail order matches the screen spec after items are removed.
- [ ] A forged call to an Administrator-only `/api/v1` endpoint from a non-administrator is refused by the gateway with `urn:pegasus:problem:not-authorized`.
- [ ] A `StaffActorFactory.TryCreate` failure ends the session rather than granting an anonymous shell.
- [ ] Rights are recomputed on every session change and never survive sign-out.
