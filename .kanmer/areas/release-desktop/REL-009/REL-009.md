## What

Finalise runbook **R1 · Desktop pilot release** and execute it once, end to end, to ship the first signed package to the pilot ring (one or two internal users) against the production gateway, with evidence for every step — including the approval record that closes capability `OPS-10`'s outstanding operator acceptance under D-004.

## Why

Proposal § 24 Phase 9 requires releasing to a pilot ring, running desktop and web in parallel, and exercising update and rollback before cutover; its exit gate demands a **proven** support runbook, not a written one. § 9.3 requires piloting every mandatory version with one or two internal users. L-02 forbids an Azure test environment, so the pilot ring on the production gateway is the only place real-Azure behaviour can be validated — which is exactly why the local Test/UAT rehearsal must pass first. This is the first ticket in the epic where a real signed package reaches a real user, and under D-004 it is also where `OPS-10` acceptance is settled rather than left outstanding indefinitely.

## Implementation steps

1. Orient: read `docs/desktop/09-release-update-and-distribution/runbooks.md` § Conventions and § R1 **in full**, then the § 5 row and area plan § 3. Call Kanmer `get_doc_gates` on this ticket id, then `take_ticket`.
2. **Operator step — confirm the approval phrase before first use.** The plan proposes the literal `FEED PUBLISH GRANTED pilot <ver>` for pilot publication and `FEED PUBLISH GRANTED prod <ver>` for production; the existing `MERGE AUTH GRANTED` keeps its single meaning (the `dev` → `main` promotion) and must not be extended. Get the operator's confirmation of the exact wording and record it in `runbooks.md` § Conventions.
3. Check R1's five preconditions and record each as met or not, with evidence: (1) the gateway release the package needs is live and recorded in `docs/operations.md` — or R8 confirmed no gateway change is needed; (2) `main` carries the commit and the `desktop/v<ver>` tag exists on it; (3) CI is green for that commit including the desktop lanes and packaging tests; (4) D-002 and D-003 are in place — signing host, certificate and `<feed>` path configured; (5) the Test/UAT rehearsal of install → update → rollback passed for **this** package, with the evidence linked.
4. R1 step 1 — on the authorised release terminal, take a clean checkout of the tagged commit, confirm `git status` is clean, and record the 40-character SHA.
5. R1 step 2 — run `pwsh ./scripts/Build-DesktopRelease.ps1 -Channel pilot -Version <ver> -SourceRevision <sha>` (locked restore, x64 Release build, `winapp package`, manifest, SBOM, hashes). Record the SHA-256 of the `.msix`.
6. R1 step 3 — **Operator step**: sign with the self-managed certificate on the signing host (`winapp package --cert` or `signtool sign /fd SHA256 /f`), **always with a timestamp** (`--timestamp` or `/tr`). Verify with `signtool verify /pa /v <pkg>.msix` and confirm the output shows both the chain and the timestamp. Hand back the verification output.
7. R1 step 4 — generate `pilot/Pegasus.appinstaller` from the template with `Version` = previous + 1 revision and `MainPackage Version=<ver>`, then run `pwsh ./eng/packaging/Test-AppInstaller.ps1` (schema, `Uri`, monotonic version, hash vs manifest). A non-zero exit stops the release.
8. R1 step 5 — **Operator step**: obtain `FEED PUBLISH GRANTED pilot <ver>` in writing and record it verbatim in the ticket.
9. R1 step 6 — publish with `eng/packaging/Publish-DesktopRelease.ps1` ([[DSK-09-10]]): upload `.msix`, `.appinstaller`, `desktop-release-manifest.json` and the SBOM to `<feed>/pilot/`, **package first and `.appinstaller` last**, keeping the previous package in place.
10. R1 step 7 — verify the feed from a workstation network position. Under D-003 this is R9 step 4, not the HTTP header check the runbook's original wording describes: from a non-publisher staff account run `pwsh ./eng/packaging/Test-FeedShare.ps1 -FeedRoot <feed> -Channel pilot` and confirm path, manifest `Version`/`Uri`, package hash and read-only ACL. Correct R1 step 7's wording in `runbooks.md` in the same task so the runbook stops describing `curl -I` against a share.
11. R1 step 8 — **Operator step**: on a pilot workstation, launch Pegasus; the App Installer prompt appears; take the update; confirm the version in Settings/Diagnostics; confirm the gateway accepts the version. Hand back a screenshot of the version screen and the transcript of `Get-AppxPackage CollisionEngineers.Pegasus`. Then take one further piece of evidence the pilot is the first place that can produce it: **one document download and one case export taken more than an hour after the production gateway's current revision started**, both succeeding. That is upstream PLAT-039's outstanding renewal check — its own `proof.md` records the deployed export as having run at roughly 15:00Z against a revision that started at 14:35Z, inside the first hour, so it proves the token renewal did not break the Box read but not that it renews. Record the revision start time, both request times and both results; a failure here is a gateway defect to raise separately, not a pilot-release defect.
12. **Operator step — close `OPS-10` with this pilot approval (D-004).** The 2026-08-24 operator decision folds capability `OPS-10`'s outstanding acceptance ("Production environment deployed directly from an authorised terminal", `docs/capabilities.md:73`, executed for releases 1–3) into this desktop pilot approval; it does not close separately against the current web client, and upstream `TICK-001` stays dropped. So the pilot approval record must say so in words: it names the gateway releases whose `OPS-10` execution it accepts — releases 1–3 plus any later gateway release this pilot ran against, taken from the `docs/operations.md` gateway release table — as well as this desktop pilot, and **the approver signs once, for both**. Record the signed text verbatim in the ticket proof beside the `FEED PUBLISH GRANTED pilot <ver>` phrase. Do not seek a second, separate `OPS-10` acceptance. The matching `docs/capabilities.md` `OPS-10` row change belongs to [[DSK-09-18]] and is not made here.
13. R1 step 9 — record the release row in `docs/operations.md` (version, date, commit, package hash, signer, channel `pilot`, compat range) **in the same task**, per `AGENTS.md` § Safety rails; the table itself is created by [[DSK-09-18]].
