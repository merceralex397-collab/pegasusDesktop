## What

Choose and wire an SBOM generator into the desktop release build, and make `dotnet list package --vulnerable --include-transitive` a per-release gate whose output is either clean or triaged in the release record. This ticket is the **single owner** of four things the board otherwise builds twice: the SBOM artefact and its generator choice, the dependency-vulnerability gate, that gate's tool contract, and its suppression register. [[DSK-08-14]] and [[DSK-10-08]] consume and extend them; neither builds a second generator, a second scanner or a second register.

## Why

Proposal § 21.2 stage 12 requires generating an SBOM and a vulnerability report as part of the release pipeline, and § 17 puts dependency scanning among the required security controls. The desktop package is **self-contained** — it carries .NET and the Windows App SDK inside the MSIX — so its dependency surface is materially larger than the gateway's container image and is shipped directly to workstations. Nothing in the repository produces an SBOM today. The area plan explicitly leaves the generator choice to this ticket rather than assuming one, and step 2's recorded comparison is the only place on the board where that choice is made on evidence — which is why the SBOM step, the gate contract and the suppression register are ratified here and consumed by [[DSK-08-14]] and [[DSK-10-08]].

4. Extend `scripts/Build-DesktopRelease.ps1` to run the generator over the desktop publish output and write `sbom.json` (or the tool's canonical name) into `artifacts/desktop-releases/<ver>/`, then add its SHA-256 to the hash list and an `sbom` entry to `desktop-release-manifest.json`.
5. **Pin the one vulnerability-gate contract in one implementation.** Check whether `scripts/Test-DependencyVulnerabilities.ps1` already exists from [[DSK-10-08]]; if it does, extend it in place under this contract and change no rule inside it, and if it does not, create it here. Either way the contract is: `[CmdletBinding()] param([ValidateSet('Low','Moderate','High','Critical')][string] $FailAt = 'High', [string] $ProjectOrSolution = './Pegasus.slnx')` with the repository script header (`Set-StrictMode -Version Latest`, `$ErrorActionPreference = 'Stop'`); it runs `dotnet list $ProjectOrSolution package --vulnerable --include-transitive --format json`, parses the result rather than trusting the exit code, prints one line per finding as `package@version severity advisory-url`, and exits `1` when any finding is at or above `-FailAt`. Moderate and Low are reported without failing. The release build calls it with `-ProjectOrSolution ./src/Pegasus.Desktop/Pegasus.Desktop.csproj`, writes the output to `vulnerability-report.txt` beside the SBOM, and fails the release on a non-zero exit. Provide an explicit `-AcceptVulnerabilities <reason>` escape that writes the triage text into the register named in step 6 **and** into the release manifest rather than silently continuing — an unrecorded waiver is the failure mode this gate exists to prevent. Record in the plan document which case applied. Never a second scanner.
6. **Pin the one suppression register**: `docs/desktop/10-security-observability-performance/dependency-audit.md`, holding one row per accepted finding — package, version, advisory id, why it is accepted, review date, and the ticket that will remove it. The script reads it and treats a listed advisory as non-fatal until its review date passes, then fails. The path sits in plan 10's folder because that is where it was first named and moving it would strand [[DSK-10-08]]'s threat-register row; ownership of its contents is here, and [[DSK-10-08]] and [[DSK-08-14]] add rows to it rather than creating a second file. Keep it under `docs/desktop/` — anywhere else fails the CI `documentation` job. Check whether the file already exists from [[DSK-10-08]] and extend it in place if so.
7. Confirm the transitive flag matters here and record why: the package is self-contained, so runtime and Windows App SDK dependencies ship inside the MSIX. State that in the script header.
8. Wire CI without adding a second step of anything. **SBOM**: check whether an SBOM step already exists in the `desktop-package` lane ([[DSK-09-05]]) from [[DSK-08-14]]. A tool restored without a pinned version turns a release build into a moving target. A vulnerability waiver without a recorded reason is worse than no gate.
