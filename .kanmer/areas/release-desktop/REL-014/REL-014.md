## What

Choose and wire an SBOM generator into the desktop release build, and make `dotnet list package --vulnerable --include-transitive` a per-release gate whose output is either clean or triaged in the release record.

## Why

Proposal § 21.2 stage 12 requires generating an SBOM and a vulnerability report as part of the release pipeline, and § 17 puts dependency scanning among the required security controls. The desktop package is **self-contained** — it carries .NET and the Windows App SDK inside the MSIX — so its dependency surface is materially larger than the gateway's container image and is shipped directly to workstations. Nothing in the repository produces an SBOM today. The area plan explicitly leaves the generator choice to this ticket rather than assuming one.

## Implementation steps

1. Orient: read the § 5 row and area plan § 3, then `scripts/Build-DesktopRelease.ps1` to see the `-SbomPath` hook and the open question [[DSK-09-04]] left. Call Kanmer `get_doc_gates` on this ticket id, then `take_ticket`.
2. **Decide and record the generator.** Compare at least Microsoft's `Microsoft.Sbom.DotNetTool` (SPDX output) and `CycloneDX.DotNet` on: dotnet-tool installability under a locked restore, output format, whether it covers a self-contained publish's runtime files, licence, and added CI minutes. Use `microsoft_docs_search` for `SBOM tool dotnet SPDX generate` and `microsoft_docs_fetch` the result. Write the comparison and the choice into the ticket research — do not pick silently.
3. Pin the chosen tool the way the repository pins everything else: a `dotnet-tools.json` manifest entry with an exact version, restored with `dotnet tool restore`, so a tool update is a reviewed change and not a surprise.
4. Extend `scripts/Build-DesktopRelease.ps1` to run the generator over the desktop publish output and write `sbom.json` (or the tool's canonical name) into `artifacts/desktop-releases/<ver>/`, then add its SHA-256 to the hash list and an `sbom` entry to `desktop-release-manifest.json`.
5. Make the vulnerability check a gate rather than an artefact: `dotnet list ./src/Pegasus.Desktop/Pegasus.Desktop.csproj package --vulnerable --include-transitive` written to `vulnerability-report.txt`, with the build failing on any `High` or `Critical` row. Provide an explicit `-AcceptVulnerabilities <reason>` escape that records the triage text into the release manifest rather than silently continuing — an unrecorded waiver is the failure mode this gate exists to prevent.
6. Confirm the transitive flag matters here and record why: the package is self-contained, so runtime and Windows App SDK dependencies ship inside the MSIX. State that in the script header.
7. Add the SBOM and vulnerability steps to the CI `desktop-package` lane ([[DSK-09-05]]) and upload both files with `actions/upload-artifact@v6` alongside the MSIX, using the same `if-no-files-found: error` discipline.
8. Measure the added CI time and record it against the C-01 cost picture: run the lane before and after, note the delta in minutes, and hand the number to [[DSK-08-19]]. If the delta is material, record whether the SBOM should run only on the tag lane ([[DSK-09-17]]) rather than every PR — decide and record, do not leave it implied.
9. Define the release-record shape: which fields of the SBOM and vulnerability report appear in the desktop release row ([[DSK-09-18]]) — at minimum the SBOM file hash and a clean/triaged flag.
10. Prove it end to end: run `pwsh ./scripts/Build-DesktopRelease.ps1 -Channel pilot -Version 1.0.<run>.0 -SourceRevision $(git rev-parse HEAD)` on a clean tree and confirm the SBOM and the vulnerability report are produced, hashed and referenced from the manifest.
11. Record the dated `## Simplification pass` in the ticket plan document over this branch's own diff.

## Guardrails

- **Azure**: no write. No Azure or third-party scanning service is introduced.
- **Scope boundary**: `scripts/Build-DesktopRelease.ps1`, a tool manifest, and the `desktop-package` CI lane. Must not change `scripts/Build-ReleaseArtifacts.ps1` or the gateway release — a gateway SBOM is a separate decision.
- **Traps**: `--include-transitive` is essential because the package is self-contained and ships its runtime; omitting it under-reports the shipped surface. A tool restored without a pinned version turns a release build into a moving target. Private-repository Windows minutes bill at 2× (C-01) — measure the added time rather than assuming it is free. A vulnerability waiver without a recorded reason is worse than no gate.
