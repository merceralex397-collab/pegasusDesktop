## What

Add a protected, tag-triggered lane that signs a desktop package with the production certificate and publishes it to the **pilot** feed after explicit approval, when a `desktop/v*` tag is pushed on `main`. Production publication stays a runbook-controlled terminal step (R2) and is not automated.

## Why

Proposal § 21.2 items 13–15 place signing in a **protected release job** only, then publication to pilot or production, then recording the package hash, version, source commit and API compatibility range. The area plan states pilot publication may be automated once the signing route is settled — D-002 and D-003 have settled it — while production stays a terminal step with explicit operator approval, mirroring the existing `MERGE AUTH GRANTED` culture without extending that literal phrase. Automating the pilot half removes the most repeated manual step while keeping the irreversible one deliberate.

## Implementation steps

1. Orient: read the § 5 row, area plan § 3 "Publication", `runbooks.md` § R1 steps 3–6 and § R2, and `.github/workflows/ci.yml` in full. Call Kanmer `get_doc_gates` on this ticket id, then `take_ticket`.
2. **Decide and record the workflow file.** `ci.yml`'s trigger block is `pull_request` + `push: branches: [main]`; adding `push: tags:` there would run all nine existing jobs on every tag. Put the lane in a **new** workflow `.github/workflows/desktop-release.yml` with `on: push: tags: ['desktop/v*']` and `permissions: contents: read`, and record the reasoning in the ticket plan so the choice is not re-litigated.
3. Guard the tag's provenance in the first job step: resolve the tag's commit and fail unless it is contained in `main` (`git merge-base --is-ancestor <tag sha> origin/main`). A tag on an unmerged branch must not produce a signed package.
4. Run the lane on the self-hosted runner that lives on the signing host: `runs-on: [self-hosted, windows, pegasus-signing]`. D-002 forbids the `.pfx` being a GitHub secret, so a hosted runner cannot sign; if the self-hosted runner is not yet available ([[DSK-08-19]] decides the runner strategy), land the workflow with the job `if: false` and an explicit comment rather than inventing a hosted-signing route.
5. Add the approval gate: put the signing/publishing job behind a repository `environment:` that requires a reviewer, and require the operator to record the literal `FEED PUBLISH GRANTED pilot <ver>` (wording confirmed by [[DSK-09-11]]) in the ticket before approving. The environment approval and the recorded phrase are both required — the phrase is the audit trail, the environment is the mechanism.
6. Job steps, in order: `actions/checkout@v7` at the tag; `./.github/actions/dotnet-build`; then `pwsh ./scripts/Build-DesktopRelease.ps1 -Channel pilot -Version <version from the tag> -SourceRevision <tag sha> -Sign -CertificatePath <host path> -TimestampUrl <timestamp service>`. Derive `<version>` from the tag name (`desktop/v1.2.345` → `1.2.345.0`) and fail if it does not match `^1\.\d+\.\d+\.0$`.
7. Verify before publishing: `signtool verify /pa /v` on the produced `.msix` must report a valid chain **and** a timestamp, and `pwsh ./eng/packaging/Test-AppInstaller.ps1` must exit `0`. Either failure aborts the job before anything reaches the feed.
8. Publish with `pwsh ./eng/packaging/Publish-DesktopRelease.ps1 -Channel pilot` — package first, `.appinstaller` last, previous package retained. The job never publishes to `prod`; add an explicit guard that refuses `-Channel prod` in this workflow, so a future edit cannot quietly widen it.
9. Upload the signed package, manifest, SBOM and hashes with `actions/upload-artifact@v6` and write the release identity (version, source commit, package SHA-256, signer thumbprint, compatibility range) into the job summary, satisfying § 21.2 item 15.
10. **Dry run first, with a development certificate to a local feed**: point `-CertificatePath` at the dev certificate from [[DSK-09-06]] and `-FeedRoot` at the Test/UAT stack's share, and run the whole lane. Only after that passes should the real certificate and the real pilot feed be used. Record both runs.
11. **Operator step** — the first real run: push `desktop/v<ver>` on `main`, record `FEED PUBLISH GRANTED pilot <ver>`, approve the environment, and confirm the pilot feed received the files. Hand back the run URL and the feed listing.
12. Write into `runbooks.md` § R1 which steps this lane now performs automatically and which remain manual, and state plainly in R2 that **production publication is never automated** — it stays the terminal step with `FEED PUBLISH GRANTED prod <ver>`.
13. Record the dated `## Simplification pass` in the ticket plan document over this branch's own diff.

## Acceptance criteria

- [ ] A `desktop/v*` tag on `main` triggers the lane; a tag not contained in `main` is refused.
- [ ] Signing happens only on the self-hosted signing host; no PFX, password or certificate is stored as a GitHub secret.
- [ ] The lane cannot publish to `prod` — an explicit guard refuses that channel.
- [ ] Publication requires both the environment approval and the recorded `FEED PUBLISH GRANTED pilot <ver>` phrase.
- [ ] `signtool verify /pa /v` and the `.appinstaller` validator both pass before any file reaches the feed.
- [ ] The release identity (version, commit, hash, signer, compat range) is recorded in the run summary.
- [ ] The nine existing `ci.yml` jobs are unaffected and do not run on tags.

## Verification

- [ ] Dry run with the dev certificate to the Test/UAT feed — expected: lane green, package signed, validator exit `0`, files present on the stack share in the correct order.
- [ ] Real run on `desktop/v<ver>` — expected: environment approval requested, lane green after approval, pilot feed carries the new `.msix`, `.appinstaller` and manifest with the previous package retained.
- [ ] `git push` of a `desktop/v*` tag pointing at a commit not in `main` — expected: the lane fails at the provenance check before building.
- [ ] `grep -n "secrets\." .github/workflows/desktop-release.yml` — expected: no certificate or password secret referenced.
- [ ] Push to `main` without a tag — expected: `desktop-release.yml` does not run; `ci.yml` behaves exactly as before.

## Guardrails

- **Azure**: no write. This lane authenticates to no cloud service; GitHub Actions Azure deployment stays `Not planned` (`docs/runbook.md:903`).
- **Scope boundary**: a new `.github/workflows/desktop-release.yml` and documentation. Must not modify the gateway release route, `scripts/Build-ReleaseArtifacts.ps1`, or `azd`/`infra` anything.
- **Traps**: the CI runner has no production certificate — signing belongs to the protected tag job on the signing host or the release terminal, never a PR build. `--timestamp`/`/tr` is mandatory. Never publish an `ms-appinstaller:` protocol link. Publishing order matters: package first, `.appinstaller` last. Private-repository Windows minutes bill at 2× (C-01) — the tag lane must not duplicate the PR lane's work beyond what signing requires. The signing host is a single point of failure for publishing and a single high-value target — the runner's isolation and permissions are specified by [[DSK-08-19]] and must be respected here.
- **Blocking prerequisite**: if the self-hosted runner does not exist yet, land the workflow disabled with a comment rather than routing signing through a hosted runner — that would require the `.pfx` as a secret, which D-002 forbids.
- **Operator-only**: pushing the release tag, recording the approval phrase, and approving the environment.
