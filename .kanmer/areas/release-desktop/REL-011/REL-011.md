## What

Finalise runbook **R4 · Rollback** and prove it: the previous known-good package is republished under a **new, higher** `.appinstaller` `Version` with `ForceUpdateFromAnyVersion="true"`, a client downgrades to it, and the gateway minimum version is lowered so downgraded clients are accepted.

## Why

Proposal § 9.3 requires keeping the previous known-good package available and defining the downgrade/rollback policy explicitly; § 24 Phase 9's exit gate requires that update **and rollback** have been exercised, and programme exit criterion 13 requires install, mandatory update and rollback all proven. Rollback is the one procedure that is only ever run under pressure, and it has two counter-intuitive rules — the `.appinstaller` version must go **up** while the package version goes **down**, and the minimum client version must be lowered **first** — either of which, missed, leaves the estate stuck.

## Guardrails

- **Azure**: no write.
- **Scope boundary**: `docs/desktop/09-.../runbooks.md`, `eng/packaging/`, `docs/operations.md`, and operator actions on the feed and pilot workstations. Must not rebuild or re-sign the previous package — rollback republishes the **same signed artefact**.
- **Traps**: the `.appinstaller` `Version` must increase even when the package version decreases — App Installer only reacts to a higher manifest version. Without `ForceUpdateFromAnyVersion` App Installer moves only to higher package versions and the rollback silently does nothing. Never overwrite a published `.msix`. Lower the gateway minimum version before publishing the rollback or every client stays blocked. Off-network clients will not see the rollback until they return to the LAN or VPN.
- **Operator-only**: obtaining the approval phrase, publishing to the feed, and relaunching on a pilot workstation.
- **Simplification pass** (`AGENTS.md` step 4): required over this branch diff before the PR, recorded under a dated `## Simplification pass` heading in the plan document.
