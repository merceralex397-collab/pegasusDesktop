## What

Write runbooks **R5 · Code-signing certificate renewal** (for the decided self-managed route only) and **R6 · Emergency block of a defective client version**, and rehearse both — R5 end to end with a throwaway replacement certificate on the Test/UAT machines, R6 on the Test/UAT stack.

## Why

Proposal § 17.1 requires a code-signing certificate protection and renewal runbook, and § 9.3 requires an emergency release path with no secret bypass. D-002 chose the self-managed certificate, which means the estate carries the renewal burden the paid routes would have absorbed — and with a ~3-year validity, renewal fires roughly once per parliament, which is exactly why it must be **rehearsed rather than remembered**. R6 is the one procedure measured in minutes: a defective version must stop doing work independently of the feed.

## Implementation steps

1. Orient: read `runbooks.md` § R5 and § R6 in full and `signing-and-hosting-decision-matrix.md` § D-002 chosen shape. Call Kanmer `get_doc_gates` on this ticket id, then `take_ticket`. **D-002 is decided** — R5 documents the self-managed route only; delete no history from the matrix but write no alternative route into the runbook.
2. Write R5 step 1: calendar the expiry in `docs/operations.md` with a **90-day warning**, next to the recorded thumbprint, subject and validity window from [[DSK-09-08]].
3. Write R5 step 2: issue the replacement on the signing host with the **same subject** as the current certificate — it must equal the manifest `Publisher` exactly, and changing it changes the package identity. Restrict the new `.pfx` to the publisher account; keep the old one until step 6.
4. Write R5 steps 3–4: export the new **public** `.cer` only, then **push trust before publishing anything signed with it** — import into `Cert:\LocalMachine\TrustedPeople` on every workstation (scripted and elevated, or by Group Policy, whichever [[DSK-09-08]] recorded). Reversing the order gives users `0x800B0109` and a failed update.
5. Write R5 step 5: verify on one machine that is **not** the publisher — `certutil -verifystore TrustedPeople` lists **both** certificates; sign a test package with the new certificate and install it.
6. Write R5 steps 6–7: only then sign releases with the new certificate; once every machine is confirmed, remove the old `.cer` from `TrustedPeople` (a decommissioned key should not keep vouching for packages); record thumbprint, subject, validity window, rollout date and confirmed machines in `docs/operations.md`.
7. Write R5's compromise variant exactly as the plan states: treat it as an emergency renewal — issue immediately, push the new trust, remove the old `.cer` **first** rather than last, re-sign the current release, and raise the gateway minimum version if a maliciously signed package could plausibly have been installed. State plainly that there is **no revocation list in a private-trust estate — removing trust is the revocation**.
8. **Operator step — rehearse R5 once, before go-live.** On the Test/UAT machines, issue a throwaway replacement certificate with the same subject, run the trust push, verify both certificates are listed, sign and install a test package, then remove the old `.cer` and confirm a package signed with the retired certificate no longer installs. Hand back every transcript. The first execution must not be the one under time pressure.
9. Write R6 step 1: raise the minimum client version above the defective version (R3 step 1) — or, when the fix is not yet built, to the last good version and publish the last good package as a rollback (R4) so clients can still work.
10. Write R6 steps 2–4: confirm a defective client is refused (`client-unsupported` problem, update-required screen); communicate to users; collect diagnostics bundles (R10); record in the release row and the security/action history. State R6's limit: it does not prove the defect's data impact — an audit query is needed.
11. **Operator step — rehearse R6 on the Test/UAT stack** and record the elapsed time from decision to a defective client being refused. That number is the operational claim; do not write a target that was not measured.
12. Mark R5 and R6 as rehearsed in `runbooks.md` with their dates, and record the dated `## Simplification pass` in the ticket plan document.

## Guardrails

- **Azure**: no write. D-002 withdrew the Azure signing routes entirely; Key Vault is not involved in certificate storage.
- **Scope boundary**: `docs/desktop/09-.../runbooks.md`, `docs/operations.md`, and the Test/UAT machines for the rehearsal. Must not touch the production certificate or the estate trust — that is [[DSK-09-08]].
- **Traps**: certificate expiry without timestamping invalidates every installed package's signature path for **new** installs — existing timestamped installs keep working, which is why the runbook says so explicitly rather than implying a fleet-wide outage. Changing the subject changes the package identity. Trust must reach devices before the app does, in both R5 and R7. There is no revocation infrastructure in a private-trust estate. Do not extend the literal `MERGE AUTH GRANTED` to signing or publishing approvals.
- **Operator-only**: issuing the rehearsal certificate, pushing trust, and running the Test/UAT rehearsals require elevated machine access.
- **Simplification pass** (`AGENTS.md` step 4): required over this branch diff before the PR, recorded under a dated `## Simplification pass` heading in the plan document (`n/a — docs-only` if the diff is documentation only).
