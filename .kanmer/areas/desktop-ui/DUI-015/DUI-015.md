## What

Wire two automated accessibility checks into the desktop UI test lane: the AutomationId coverage audit derived from `winapp ui inspect --interactive --json`, and an `AxeWindowsCLI` scan of the running app that produces an archived report and fails the lane on a critical finding.

## Why

The area's exit gate requires 100% AutomationId coverage and no critical `axe-windows` findings on every shipped page (`docs/desktop/06-ui-design/README.md` § 4). Without automation these are review rules nobody re-runs. Operator-visible consequence: a control that a screen reader or automation cannot reach is caught before it ships. Consumes the CI lanes from plan 08; feeds the recorded reviews in [[DSK-06-16]].

## Implementation steps

1. Orientation. Read the plan row, `docs/desktop/06-ui-design/keyboard-and-accessibility.md` § Automated checks, and `docs/desktop/08-testing/README.md` § 5 rows `DSK-08-06`, `DSK-08-09`, `DSK-08-12`, `DSK-08-13`. Confirm the UI harness and the CI lanes exist; if `DSK-08-12` decided hosted runners cannot do this, follow its recorded decision instead of forcing it. Call Kanmer `get_doc_gates` for this ticket id, then `take_ticket`.
2. Load `pegasus-desktop`, then `winui-ui-testing`. Read its Accessibility Audit block — the filter and the failure shape are specified there; reuse them rather than writing a new audit.
3. Add `tests/Pegasus.Desktop.UITests/Invoke-AutomationIdAudit.ps1` taking `-AppPid` and an optional `-Screen` label. It runs `winapp ui inspect -a $AppPid --interactive --json`, filters to app elements (types matching `Button|TextBox|ComboBox|CheckBox|ToggleSwitch|TabItem|Edit|ListItem|Hyperlink`, excluding window chrome names `Minimize|Maximize|Close|System` and OS dialog classes `PickerHost|#32770|CabinetWClass`), and fails with the list of offending `type 'name'` values when any lacks `automationId`. Emit `artifacts/a11y/<screen>-automationids.json`.
4. Add `tests/Pegasus.Desktop.UITests/Invoke-AxeScan.ps1` running `AxeWindowsCLI.exe --processid <PID> --outputdirectory artifacts/a11y --verbosity default` per the plan's automated-checks table. Parse the produced report, classify findings by severity, and exit non-zero on any critical finding. Record the tool version in the output so a report can be traced to a build.
5. Acquire `AxeWindowsCLI` deterministically: pin the version and record how it is obtained (a pinned download step or a checked-in tool manifest entry). Do not fetch "latest" at run time — a scanner that changes silently makes a green lane meaningless.
6. Drive both scripts from the per-screen loop: for every shipped screen, navigate to it with `winapp ui invoke` on its rail item or entry control, wait for a screen-specific element, then run the audit and the scan. The screen list comes from the FRD-13 sections adopted by [[DSK-06-13]].
7. Wire into CI: extend the `desktop-ui-smoke` lane in `.github/workflows/ci.yml` (created by `DSK-08-13`) to run both scripts after the app is installed and launched, upload `artifacts/a11y/**` as a workflow artifact, and fail the job on a non-zero exit from either. Load `authoring-github-workflows` for the job and artifact syntax.
8. Make the failure message actionable: on an AutomationId miss print the control type, its visible name and the screen; on a critical axe finding print the rule id and the element's `AutomationId`. A failure an engineer cannot act on is a flaky lane in waiting.
9. Measure the runtime cost of the added lane (wall-clock minutes on `windows-latest`) and record it in the ticket, because private-repository Windows minutes bill at 2× under constraint C-01 — hand the figure to `DSK-08-19`.
10. Record the boundary explicitly in the lane's output and in the ticket: these two checks are automated evidence only. `docs/engineering.md` tier 7 states that automated axe results do not replace the manual keyboard or assistive-technology review, which [[DSK-06-16]] owns.
11. Prove the gate bites: introduce a control without an `AutomationId` on a scratch branch, run the lane, confirm it fails with the control named, then revert. Attach the failing run's output to the ticket.
12. Run the full lane against every currently shipped screen and attach the artifact set as the ticket's proof.

## Acceptance criteria

- [ ] The AutomationId audit reports 100% coverage on every shipped page and fails the lane otherwise, naming the offending controls.
- [ ] `AxeWindowsCLI` runs against the live process per screen and archives its report as a CI artifact.
- [ ] A critical axe finding fails the lane.
- [ ] The scanner version is pinned and recorded in the output.
- [ ] The lane's added runtime is measured and handed to the CI cost ticket.
- [ ] The output states that automated results do not replace the manual keyboard and assistive-technology reviews.
