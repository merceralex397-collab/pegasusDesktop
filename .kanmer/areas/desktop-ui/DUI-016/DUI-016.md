## What

Establish the ten recorded accessibility reviews as a repeatable per-screen, per-release-candidate procedure: a checklist, the exact evidence file format, where the files live, and who signs each review — then run it once end to end on the current release candidate to prove the procedure works.

## Why

The design authority requires ten recorded reviews for any planned surface with a real caller (`docs/design/README.md:798-808`), and the programme exit checklist items 11–12 depend on them. Operator-visible consequence: keyboard-only, screen-reader, 200%, forced-colours and reduced-motion behaviour is checked by a person before a build reaches an operator, and the result is attributable. Consumes [[DSK-06-15]]; feeds the release-candidate proof in plan 09.

## Implementation steps

1. Orientation. Read the plan row, `docs/desktop/06-ui-design/keyboard-and-accessibility.md` § The ten recorded reviews and § Acceptance, and `docs/design/README.md:798-808`. Call Kanmer `get_doc_gates` for this ticket id, then `take_ticket`.
2. Load `pegasus-desktop`, then `winui-ui-testing`. Write the checklist as `docs/desktop/06-ui-design/keyboard-and-accessibility.md` content only — no new `.md` outside `docs/(prd|frd|adr|design|desktop)`, or the CI `documentation` job fails.
3. For each of the ten reviews record, in one table: what is exercised, whether it is scripted or manual, the exact command or setting used, the evidence artefact it produces, and who signs it. Reviews 1–3 are scripted plus a manual pass; 4–8 are settings-driven screenshot passes; 9 is a measurement; 10 is the [[DSK-06-15]] lane.
4. Write the exact procedure per review, with the commands: (1) keyboard-only traversal — `winapp ui send-keys` journey from [[DSK-06-14]] plus a manual pass, screenshot of focus at each stop; (2) screen-reader and semantic inspection — Narrator script plus `winapp ui inspect -a <PID> --interactive --json` tree export; (3) focus and error behaviour — dialog trap and return, error summary, field association; (4) 1280+ screenshots; (5) 1024–1279 constrained review confirming secondary content reorders and nothing is hidden; (6) 200% zoom via Windows display scaling with `winapp ui screenshot`; (7) forced colours under a Windows Contrast theme; (8) reduced motion with `UISettings.AnimationsEnabled` off, confirming the static `Working` equivalent; (9) contrast review measuring the token pairs from `docs/desktop/06-ui-design/tokens-and-theme.md`; (10) the `AxeWindowsCLI` report.
5. Fix the evidence format exactly as the plan states — one file per screen per release candidate at `artifacts/a11y/<release>/<Screen>.md`, containing: screen, build version, channel, date, reviewer; a table of `review # | result (pass/fail) | evidence path | notes`; and a findings list of `id, severity, rule, element AutomationId, disposition (fixed in <ticket> | accepted with reason | deferred to <ticket>)`. Add the template file for one screen as the worked example.
6. State the disposition rule: a failed review is either fixed in a named ticket, accepted with a recorded reason, or deferred to a named ticket. "Noted" is not a disposition, and an unresolved failure blocks the release candidate.
7. Add a driver script `tests/Pegasus.Desktop.UITests/Invoke-RecordedReviews.ps1 -Release <tag> -Screen <name>` that runs every scripted part, creates the per-screen file pre-filled with the scripted results, and leaves the manual rows blank for the human passes. It must never mark a manual review as passed.
8. Record who signs what: `pegasus-ui-verifier` produces the evidence and never fixes findings; `pegasus-desktop-reviewer` records the design-authority review (four hard rules, banned words, status vocabulary, one primary action, no colour-only state) in the ticket plan; the operator signs the reviews that need a person at the workstation.
9. **Operator step** — reviews 1, 2, 6, 7 and 8 need a human at a Windows 11 workstation: a keyboard-only pass without touching the mouse, a Narrator pass, a 200% display-scale pass, a Contrast-theme pass and a reduced-motion pass. Evidence to hand back: the signed rows in each `<Screen>.md` with the reviewer's name and date, plus the screenshots the script could not take under those system settings.
10. Run the whole procedure once, end to end, on the current release candidate across every shipped screen, and attach the resulting `artifacts/a11y/<release>/` set as the ticket's proof (`set_ticket_doc` proof, types `visual` and `command-log`).
11. Wire it into the release ticket: record in `docs/desktop/09-release-update-and-distribution/README.md`'s release checklist that a release candidate is not signed off until every shipped screen has its ten-review file with no unresolved failure.
12. Record the elapsed time the full pass took per screen, so the release cadence can plan for it honestly rather than discovering it at cutover.
