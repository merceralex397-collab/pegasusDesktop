## What

Implement the whole keyboard map from `docs/desktop/06-ui-design/keyboard-and-accessibility.md` § Keyboard map as `KeyboardAccelerator`s and access keys, with discoverability through KeyTips and tooltips and a Keyboard list on the Diagnostics screen — and prove each shortcut with a scripted journey.

## Why

Proposal § 14.9 makes full keyboard completion of every critical workflow a baseline, and the programme exit checklist item 12 requires it. Operator-visible consequence: an operator who never touches the mouse can navigate, search, create, save, close, refresh and dismiss. Depends on the shell [[DSK-06-04]]; consumed by the scripted keyboard journeys in [[DSK-08-07]].

## Implementation steps

1. Orientation. Read the plan row and `docs/desktop/06-ui-design/keyboard-and-accessibility.md` § Keyboard map in full — it is the specification, row by row, and includes the recorded deviation that `Ctrl+K` focuses the Cases search box (navigating to Cases first) rather than opening a global search screen. Call Kanmer `get_doc_gates` for this ticket id, then `take_ticket`.
2. Load `pegasus-desktop`, then `winui-design`. Search `microsoft_docs_search` for `KeyboardAccelerator` scoping and `AccessKey` KeyTip display in WinUI 3 before wiring anything, so app-level versus element-level scope is right the first time.
3. Register the global accelerators once, on the shell, as `KeyboardAccelerator`s bound to shell-level commands: `Ctrl+K` (focus Cases search, navigating to Cases first), `F5` and `Ctrl+R` (refresh the current screen — the same command the page header exposes, [[DSK-06-12]]), `Esc` (close the transient pane, flyout or dialog; clear a focused search box), `F6` (cycle rail → header → content → status).
4. Register the screen-scoped accelerators on the content frame so they resolve against the active screen: `Ctrl+N` (the context-appropriate new item — Cases → New case, Upload → pick file, Administration lists → Create; disabled where the user lacks the right, with the server authorising regardless), `Ctrl+S` (save the current editable view; a no-op with status-bar text when nothing is dirty), `Ctrl+W` (close the record view back to its list, warning through the `ReasonDialog`-shaped confirmation when unsaved changes exist), `Ctrl+1`…`Ctrl+8` (select tab n in a record workspace, in displayed order).
5. Rail access keys: set `AccessKey` on each rail item so `Alt` shows KeyTips — `Alt+D` Dashboard, `Alt+I` Inbox, `Alt+U` Upload, `Alt+Q` Queues, `Alt+C` Cases, `Alt+O` Operations, `Alt+A` Administration. `Administration` and `Inbox` KeyTips exist only when the items are present.
6. List navigation is the platform's: `↑`/`↓`, `Home`/`End`, `PageUp`/`PageDown` in lists, `Enter` or double-click to open, `Space` to toggle selection or invoke a focused button, `Shift+F10`/`Menu` for the row context menu, `Alt+↑`/`Alt+↓` between table header and first row (implemented with the table pattern, [[DSK-06-07]]). Verify rather than re-implement; virtualized lists must keep selection.
7. `Ctrl+C` copies the selected reference, plate or Reference value on record headers and on the problem Reference row ([[DSK-06-10]]) — only that value, nothing else.
8. Focus order: title bar → rail → page header → content → status bar, and initial focus per screen type (lists focus the first row, or the search box when empty; forms focus the first field; dialogs focus the reason box; the Update-required screen focuses `Update.Required.Now`). Verify with `winapp ui get-focused` after each navigation.
9. Conflicts: confirm no accelerator collides with a Windows system shortcut (`Win+*`), with `NavigationView` defaults, or with the reason dialog's safety rule that `Enter` never confirms a destructive action (`DefaultButton=Close`, [[DSK-06-09]]). Record the check in the ticket.
10. Discoverability: every shortcut appears in its control's tooltip (`KeyboardAccelerator` tooltips are automatic when `ScopeOwner` and `AccessKey` are set correctly) and in a Keyboard section on the Diagnostics screen — a list of shortcut and action, not explanatory prose (`docs/design/README.md:422-445`).
11. Build and run with `pwsh .codex/skills/winui-dev-workflow/BuildAndRun.ps1 src/Pegasus.Desktop/Pegasus.Desktop.csproj`. Load `winui-ui-testing` and write `tests/Pegasus.Desktop.UITests/keyboard-tests.ps1` using `winapp ui send-keys "<combo>" --via send-input` followed by `wait-for`/`get-focused` for every row of the map, plus a single keyboard-only journey: sign in → `Alt+C` → `Ctrl+K` → type a reference → `Enter` → `Ctrl+1`… → `Ctrl+W` → sign out.
12. Take a focus screenshot at each stop of the journey (`winapp ui screenshot`) so the visible-focus evidence for review 1 of the ten recorded reviews ([[DSK-06-16]]) already exists.

## Acceptance criteria

- [ ] Every row of the keyboard map works as written, including the `Ctrl+K`-to-Cases deviation.
- [ ] Rail access keys show as KeyTips on `Alt`, and only for items that are present.
- [ ] `Ctrl+S` is a no-op with status-bar text when nothing is dirty; `Ctrl+W` warns before discarding unsaved changes.
- [ ] Focus order is title bar → rail → page header → content → status bar, with the specified initial focus per screen type.
- [ ] No conflict with Windows system shortcuts, `NavigationView` defaults, or the reason dialog's Enter safety.
- [ ] Every shortcut is discoverable in a tooltip and listed on the Diagnostics screen without explanatory prose.
- [ ] A keyboard-only journey completes sign in → open case → tab → close → sign out.
