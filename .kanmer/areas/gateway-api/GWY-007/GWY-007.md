## What

Add the read half of the case surface to `/api/v1`: a paged, sorted, filtered case list, a sectioned case detail whose sections load independently, and the case history/audit reads — all projecting the same Core query ports the Razor pages use.

## Why

Proposal § 10.6 requires server paging/filtering/sorting and case detail loaded in sections "so the first useful view appears quickly"; § 14.4–14.5 make the work queue and case workspace the Phase 3 vertical slice. Operator-visible consequence: the case list opens as fast as the web list and shows the same rows in the same order, and a case workspace paints its header before the heavy sections arrive. Today `Cases/Details.cshtml.cs` loads one fat `CaseDetails` record; reproducing that on the desktop would put a multi-second wait in front of every case open.

3. Add `src/Pegasus.Contracts/Cases/` response DTOs: `CaseListItemResponse`, `CaseHeaderResponse` (header + overview + `version`), and one response per section named for the section route. Do not expose `CaseDetails` or any Core record directly.
4. Add `src/Pegasus.Web/Api/CaseReadEndpoints.cs` mapping a `cases` sub-group with `.RequireStaffRight(StaffAccessRight.PerformCasework)`. Map `GET /` (list), `GET /{id}` (header+overview) and the seven section routes `/{id}/vehicle`, `/{id}/assessment`, `/{id}/documents`, `/{id}/communications`, `/{id}/tasks`, `/{id}/reports`, `/{id}/history`.
5. Bind the list query parameters onto `CaseSearchFilters` exactly: `stage` → `State`, `assignee` → `EngineerId`, `principal` → `Principal`, `q` → `Query`, plus the date filters the record already carries. Reject any `sort` value that is not a `CaseSearchOrder` name with a 400 `urn:pegasus:problem:validation` problem — that is the sort whitelist from § 3.
6. Default `sort` to `CaseSearchOrder.ReceivedDesc` and `pageSize` to 25 with a hard cap of 200; return `PagedResult<T>` from `src/Pegasus.Contracts` with `TotalCount` **null**, because `SearchCasesResult` supplies only `HasPreviousPage`/`HasNextPage`.
7. Return `version` in the `GET /cases/{id}` body and a weak `ETag` (`W/"<version>"`) per § 3 row *Concurrency*; give each section its own `ETag` and honour `If-None-Match` with 304. `If-Match` is **not** the concurrency mechanism — do not accept it.
8. Make each section route hit only the ports that section needs, so a case header does not pay for documents or assessment. Where the only available port today returns the whole `CaseDetails`, project the section from it but record the N+1/over-fetch in the ticket plan as a follow-up rather than adding a new Core query without a decision.
9. Add `GET /audit` in the same group: `PerformCasework` returns history for a case the caller may see; the unfiltered actor/date search requires `ManageStaffAccounts` per the endpoint-map row. Reuse the action-history / security-event read ports at `src/Pegasus.Core/Identity/IdentityContracts.cs:98-137`.
10. Run the `optimizing-ef-core-queries` skill over the EF implementations behind `ICaseQueryStore` (`src/Pegasus.Infrastructure/Persistence/`) that the list and section routes exercise, and record the findings in the ticket plan. Done means no new N+1 introduced by the section split.
11. Add `tests/Pegasus.IntegrationTests/DesktopGatewayCaseReadTests.cs` covering: paging (page 1 and 2 boundaries, `HasNextPage`), the newest-first default, each whitelisted `sort` value, each dropdown filter, an invalid `sort` returning a `validation` problem, each section returning independently with its own `ETag`, `If-None-Match` returning 304, and a list/detail comparison against the Razor pages for the same seeded data.
