## What

An agent that implemented none of the endpoint tickets audits every `/api/v1` command endpoint for the seven-case test matrix and the correct `StaffAccessRight`, produces a `test-gap-analysis` report in the ticket, and files a Kanmer ticket for each gap found.

## Why

The plan's exit gate (§ 4) requires that *every* command endpoint has tests for authorized success, unauthorized, version conflict, lease conflict, operation-key replay, validation failure and the problem-details shape — and that every list endpoint has paging/filter/sort and newest-first tests. Nine separate endpoint tickets each assert their own coverage; only an independent pass over the whole surface can say the set is complete. Operator-visible consequence: no command reaches the pilot ring with an untested authorization path, which is the failure mode that turns into a silent data change by the wrong person.

## Implementation steps

1. Orient. Read `docs/desktop/03-gateway-api-and-data/README.md` § 4 and § 7 in full and `endpoint-map.md` end to end. Confirm you implemented none of [[DSK-03-06]]–[[DSK-03-15]]; if you did, hand the ticket to another agent. Then `get_doc_gates <this ticket id>` and `take_ticket`.
2. Build the authoritative route inventory from the running server, not from the source: boot `WebApplicationFactory<Program>` with `Features:DesktopGateway=true` and enumerate `EndpointDataSource.Endpoints` filtered to `/api/v1`. Save the list as the ticket's reference document.
3. Cross-check that inventory against every row in `endpoint-map.md`: every mapped row has a route, every route has a row, and each route's declared `StaffAccessRight` matches its row's **Auth right** column. Record differences as findings — an extra undocumented route is as much a finding as a missing one.
4. For each command route, verify by reading the test files that all seven cases exist and actually assert: authorized success, unauthorized (wrong role), version conflict returning the current version, lease conflict, operation-key replay returning the same result, validation failure, and the problem-details shape (`type` URI plus `correlationId`).
5. For each list route, verify the paging, filter, sort and newest-first-default tests exist and that the sort whitelist is actually enforced (a test that only asserts a 200 is not coverage).
6. Run the `test-gap-analysis` skill over `tests/Pegasus.IntegrationTests` and `tests/Pegasus.Api.ContractTests` scoped to the `DesktopGateway*` and contract test classes, and attach its report to the ticket with `set_ticket_doc`.
7. Run the `assertion-quality` skill over the same test classes and record every weak assertion (status-code-only facts, assertions on a message string where a type is available, facts with no arrange-time precondition).
8. Verify the two structural gate facts still hold: `Features:DesktopGateway=false` leaves no `/api/v1` route (the 404 fact from [[DSK-03-02]]), and the OpenAPI snapshot plus previous-snapshot compat test pass (from [[DSK-03-04]] and [[DSK-03-17]]).
9. Check the three cross-cutting traps by reading the code, not the tests: no business rule lives in an endpoint filter ("two policy engines"); no endpoint reproduces `Pages/Cases/CaseMutationPageModel.cs`'s TempData lease/proposed-value chaining; and no new table shipped without a `Grant*` migration — run `pwsh ./scripts/Test-MigrationGrants.ps1` to confirm.
10. File one Kanmer ticket per gap with `create_item` in the `gateway-api` area, group `EPIC-004`, profile `fix` for a defect or `feature` for missing coverage, each naming the exact route, the missing case and the test file it belongs in. Do not fix the gaps in this ticket.
11. Write the review summary into the ticket's `proof` document: the route inventory count, the number of command routes audited, the seven-case coverage table, and the list of filed ticket ids.
12. Run `pwsh ./scripts/Test-MigrationGrants.ps1` and the full gateway test filter one final time and record the command output as `command-log` proof.
