## Approach

Treat this as **one audit pass over a surface ten other tickets built, plus four small pieces
of new code**, rather than twelve independent changes. The audit order matters: compression
first (it is the only change that can break something already working), then the `ETag` helper
(which de-duplicates whatever the endpoint tickets each invented), then cancellation and
timeouts (which are additive), then the two test suites, then the measurement. The alternative
considered and rejected was **doing the hardening inside each endpoint ticket as it lands** —
which is how the duplication in step 4 arises in the first place. It was rejected because
plan 03 § 5 sequences `DSK-03-17` explicitly *after* `DSK-03-07…15` ("the whole endpoint
surface must exist before it can be hardened as a set", ticket body *Depends on*), and because
a cross-cutting rule enforced ten times independently is ten chances to diverge; enforcing it
once, over a finished surface, with an assertion that fails if it drifts, is the repository's
stated one-source-of-truth habit (`Directory.Build.props:10-17`).

The second choice worth naming: **named `IHttpClientFactory` clients rather than a per-call
`CancellationTokenSource` timeout.** Proposal § 15.2 says "Use a single shared HTTP client
pipeline through `IHttpClientFactory`" and § 16.2 says "Timeouts are provider-specific"; a
per-call token source would satisfy the second while contradicting the first, and would leave
the three `TryAddSingleton(HttpClient)` registrations in place — the actual defect.

## Steps

These refine the ticket body's implementation steps: same order, same ownership, same file
paths, adding the *how*.

1. **Orient and take the ticket.** Read `docs/desktop/03-gateway-api-and-data/README.md` § 3
   rows *Compression* (`:184`), *Concurrency* (`:181`) and *Retry* (`:187`), § 2 assumptions
   A-1 and A-4 (`:150-158`), and § 4. Read
   `docs/desktop/10-security-observability-performance/README.md` for the budgets this must
   meet — noting `:100`, that no budget is pass/fail until [[PLAT-010]] (plan handle
   `DSK-10-10`) records the baseline. Then `get_doc_gates GWY-017` and `take_ticket`.
2. **Fetch the documentation and record the date.** `microsoft_docs_fetch` on
   <https://learn.microsoft.com/aspnet/core/performance/response-compression>. Confirm three
   things specifically: the .NET 10 configuration shape for `AddResponseCompression`, the
   default MIME-type set (so the JSON-only restriction is expressed as a *replacement*, not an
   addition), and how a response is excluded. Append the fetch date to this ticket's `research`
   document under **Facts**.
3. **Register compression, JSON and problem only.** In `src/Pegasus.Web/Program.cs`, add
   `AddResponseCompression` configured for exactly `application/json` and
   `application/problem+json` — do not append to `MimeTypes.Default`, replace it — and add the
   middleware stage after `UseRouting` (`:796`) and before `UseRateLimiter` (`:819`) so the
   endpoint is known and the limiter's 429 body is still compressible. Scope it to `/api/v1` so
   `MapRazorPages()` (`:959`) and `MapStaticAssets()` (`:952`) are untouched (assumption
   A-GWY017-2). Then walk every byte endpoint from [[GWY-010]] (`DSK-03-10`), [[GWY-011]]
   (`DSK-03-11`) and [[GWY-014]] (`DSK-03-14`) — the `/api/v1` projections of the seven
   `return File(...)` handlers listed in `files` — and assert each is excluded. Range support
   is why: compression changes the byte offsets a range refers to.
4. **One `ETag` helper, not ten.** Read every read endpoint under `src/Pegasus.Web/Api/`.
   For each, confirm it emits a weak `ETag` of the form `W/"<version>"` and honours
   `If-None-Match` with `304` and no body. Where it does not, add it **through the helper in
   `src/Pegasus.Web/Api/GatewayResilience.cs`**; where an endpoint ticket invented its own
   variant, delete the variant and call the helper. Do not introduce `If-Match` — plan 03 § 3
   *Concurrency* rules it out by name. For list and rail-count responses that have no aggregate
   version (assumption A-GWY017-5), derive the validator from the page's identifiers and
   versions and keep it weak.
5. **Cancellation, handler by handler.** Read every handler under `src/Pegasus.Web/Api/` and
   confirm the `CancellationToken` it receives from `HttpContext.RequestAborted` reaches every
   Core call and every provider call. Keep a written list of every handler that ignored it —
   the list goes in the post-implementation report — and fix all of them in this branch.
   Preserve the existing surfacing decision: `src/Pegasus.Web/Mcp/AutomationMcpErrors.cs:61-64`
   rethrows `OperationCanceledException` unchanged, so cancellation must **not** be mapped onto
   a problem type.
6. **Provider timeouts in one place, named clients at the seam.** Add the timeout constants to
   `src/Pegasus.Web/Api/GatewayResilience.cs` — one named constant per provider (DVLA/DVSA
   vehicle lookup, Graph mail read, Box operation), each with a one-line comment saying why the
   number is what it is, following the `PlaywrightVersion` pattern at
   `Directory.Build.props:10-17`. Then replace the three first-wins registrations in
   `src/Pegasus.Infrastructure/DependencyInjection.cs` — `:531-534`, `:566-569`, `:608-611`,
   all `TryAddSingleton(static _ => new HttpClient { Timeout = TimeSpan.FromSeconds(100) })` of
   the *same* service type — with `IHttpClientFactory` named clients per provider (proposal
   § 15.2, "a single shared HTTP client pipeline"), and re-point the four adapter registrations
   at `:536` (`BoxContentClient`), `:570` and `:617` (`GraphMailClient`), `:589`
   (`DvlaDvsaProductionAdapter`) and `:612` (`GraphApprovedMailboxResolver`). The constant is
   referenced, never re-typed. **Note the boundary:** the ticket's Guardrails list
   `src/Pegasus.Web/Api/**`, `Program.cs` and the two test projects; this step necessarily
   touches `Pegasus.Infrastructure`. Keep the change additive and minimal and call it out in
   the PR description for the reviewer.
7. **Assert the retry rule instead of restating it.** The endpoint map's **Idempotent?** column
   (`endpoint-map.md:22-23`) already distinguishes `yes (key)`, `GET` and neither. Add a test in
   `tests/Pegasus.Api.ContractTests` that reads the generated OpenAPI document and fails if any
   non-`GET` operation is marked retryable. This is an assertion over the document, not a new
   annotation on the endpoints.
8. **The compat-range fact.** First confirm what [[GWY-004]] actually emits: if only
   `openapi/pegasus-v1.json` exists, create `openapi/pegasus-v1.previous.json` from the last

   "current" is trivially green and must not be presented as a compatibility guarantee. Then
   add `tests/Pegasus.Api.ContractTests/PreviousContractRangeTests.cs`: for the supported
   client range, exercise every operation described by the previous snapshot against the
   current in-process server and assert each response still validates against the **previous**
   schema. A removed field or a narrowed type must fail. If this needs a schema-validation
   package (assumption A-GWY017-1), add it with a pinned version and update
   `packages.lock.json`; do not lower `TreatWarningsAsErrors` (`Directory.Build.props:8`).
9. **Cancellation facts.** In `tests/Pegasus.IntegrationTests/DesktopGatewayResilienceTests.cs`
