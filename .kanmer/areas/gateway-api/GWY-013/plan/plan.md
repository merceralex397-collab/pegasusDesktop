# Plan — GWY-013: DSK-03-13 · Triage, Unidentified, image-intake and Operations endpoints as explicit named commands

## Governing documents

- No canonical document is linked yet. Retain the ticket's existing `docs_todo` state; do not invent or link a proposed desktop ADR.

## Chosen approach

Project the triage, unidentified, image-intake and operations surfaces onto `/api/v1`, turning the twelve-case action dispatcher in `Pages/Triage/Details.cshtml.cs` into twelve explicit named command routes, adding the staff promote path on unidentified resolve, and adding the operations snapshot with its two audited retry/revoke commands.

## Routing and constraints

- Future owner: `pegasus-gateway-dev`; tests: `pegasus-test-engineer`; independent review: `pegasus-desktop-reviewer`.
- Use `dotnet-webapi`, `optimizing-ef-core-queries` where the ticket changes a query, and `run-tests` for the actual runner profile. The project decision overrides generic “service per endpoint” advice: route handlers translate to existing `Pegasus.Core` ports; no second policy/service layer is introduced.
- The shared EPIC context binds this to versioned `/api/v1` route groups in the existing `Pegasus.Web`, the existing rate-limiter mechanism, an OpenAPI snapshot, and no Azure write.

- Microsoft Learn (fetched 2026-08-24): [ASP.NET Core OpenAPI support](https://learn.microsoft.com/aspnet/core/fundamentals/openapi/overview?view=aspnetcore-10.0) confirms first-party OpenAPI generation. Use the repository’s planned committed snapshot and contract-test flow rather than adding a parallel API documentation path.

7. **Give `POST /unidentified/{id}/resolve` the staff promote path (upstream INTK-035 — absorbed here and in [[DSK-05-12]]; there is no fork ticket for it).** Today the route is a bare resolve, so an Unidentified triage request whose registration never gets extracted can never be promoted. Fix the contract and the orchestration together:
   - **The request members.** `ResolveUnidentifiedRequest` (`UnidentifiedContracts.cs:245-253`) carries `expectedVersion`, `actor`, `operationKey` (≤ 200), `reason`, `targetKind`, `targetId`, an optional `targetReference` and `resolvedAtUtc`. Surface them on the wire in that shape and add exactly one new member: an **optional** `registration` (staff-typed, free text). `targetKind` is **required** — it always was in Core, and the endpoint-map row that lists only `expectedVersion`/`operationKey`/`reason` is an incomplete row, not a narrower contract. `targetId` is required for every target kind **except** the promote case: when `registration` is present, `targetId` is absent and this endpoint derives it. `registration` is accepted **only** with `targetKind = Triage`; supplied with any other kind it is a validation failure. **An ordinary resolve — every caller that exists today — sends no `registration` and behaves exactly as it does now.**
   - **The promote orchestration.** With `registration` present and `targetKind = Triage`: normalise the input through `ImageIntakeLifecycle.NormalizeRegistrationInput` (`src/Pegasus.Core/ImageIntake/ImageIntakeLifecycle.cs:174`), the source's stated one owner of that conversion — write no second normaliser and no endpoint-side format check. Look up whether the item's **originating receipt** already has a Triage (step 8); if it does, use that Triage's id and create nothing. Otherwise call `ICreateTriageFromIntake` (`TriageContracts.cs:138`) with a `CreateTriageFromIntakeRequest` built from the originating receipt's `TriageOrigin` and the normalised registration, letting `TriageLifecycleRules.ValidateCreate` (`TriageLifecycle.cs:13`) be the one judge of whether the registration is acceptable — an invalid one is refused there and nothing is created. Then call the existing `ResolveUnidentified` with `TargetKind = Triage` and `TargetId` = that Triage's id, so `EnsureDestinationExistsAsync` (`UnidentifiedContracts.cs:362-390`) passes against a Triage that genuinely exists and the resolution is recorded against the item exactly as any other resolution is. `ICreateTriageFromIntake` thereby gains its second, staff-initiated caller beside `DurableIntake.CreateTriageIfQualifyingAsync` (`DurableIntake.cs:893`) — it does not gain a second implementation.
   - **Idempotency and audit are unchanged.** The whole promote is keyed by the one `operationKey` the resolve already carries: a replay returns the same result and never creates a second Triage.
8. **Resolve the origin-receipt lookup before step 7 can run.** Upstream INTK-035 cites `ITriageQueries.GetByOriginReceiptAsync` as existing plumbing; the fork's `ITriageQueries` (`TriageContracts.cs:288-294`) carries only `ListAsync` and `GetAsync`, because that member arrives with the unmerged upstream INTK-033 — imported on this board as **upstream INTK-033 (board [[INTK-007]])**.
